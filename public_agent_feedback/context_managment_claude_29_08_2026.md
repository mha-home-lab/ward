Good instinct — and having actually checked the code, I can tell you exactly where the gap is, not just guess at it.

**The honest ceiling first, because it shapes everything else:** WARD's Go binary has no hook into the actual LLM context window — it can't see token counts, it can't know when the harness (Claude Code/opencode) is about to compact or truncate. So "context management" for WARD was never going to mean "detect fullness and react" — it can only mean "make offload and reload cheap and mechanical enough that the agent doesn't need to hold everything in its head, and structure the protocol so compaction happens at predictable points rather than being left to judgment." That's a real, achievable scope. Worth being explicit about it so the next design doesn't overpromise.

**What's actually there, and it's solid on one side:** `capture` at task completion is a genuine offload primitive — a task's raw exploration collapses into one verified artifact (summary + `verify_cmd`), and the theory is the agent can forget *how* it got there and only needs to trust *what got verified*. `ward memory context <query>` is a real, disciplined reload primitive too — FTS5-scoped, compact block, no full content dumped. Both halves exist.

**The gap, confirmed in code, not guessed:** I checked `taskRunCmd` directly — it builds the workflow, starts the engine, executes, captures on completion. Nowhere in that path does it call the context/brief lookup before running the task. Reload is currently **100% protocol trust** — `AGENTS.md` tells the agent "check `ward brief` first," but nothing mechanically injects scoped prior knowledge into the executed prompt. For a quick task that's a minor gap. For the long-running-solo-session product you've now committed to, it's a real one: if the agent skips or forgets that step three tasks deep into a long session, it silently re-derives from scratch, and the entire memory thesis quietly stops paying for itself without anyone noticing — which is exactly the kind of failure this project's own philosophy says shouldn't be trusted to happen "usually."

**The second, sharper gap: there's no mid-task checkpoint.** `tick` exists, but it's a lightweight progress note, not a context-shedding primitive. `capture` only fires at task *close*. Nothing currently lets an agent say, twenty tool calls deep into one genuinely hard task that hasn't finished yet: "here's what I've learned so far, treat it as provisionally trustworthy, and let me discard the raw exploration that produced it." That's precisely the scenario a long solo session hits hardest — not many small tasks (task-boundary capture handles that fine), but one hard task that's long *within itself*.

**Concretely, I'd build two things:**

1. **Wire scoped context injection directly into `task next`/`task run`**, not as an agent-remembered step but as a mechanical one — before generating the node prompt, pull `memory context` scoped to the task's tags/topic and prepend it. Make reload structural, not something that depends on the agent's discipline every single time.
2. **Add a real mid-task checkpoint command** — something like `ward task checkpoint <id> "<summary>" [--verify CMD]` — a partial capture that doesn't close the task but gives the agent a legitimate, protocol-sanctioned point to say "compact and forget the raw path now." This is the one genuinely missing primitive, not a refinement of an existing one.

And I'd pair both with an `AGENTS.md` rule that's structural rather than reactive — since WARD can't see the context window, don't try to write a rule like "compact when you're getting full" (unenforceable, unverifiable). Write it as "checkpoint before starting a new sub-goal, or every N tool calls" — a rule the agent can actually follow deterministically, in keeping with how every other rule in that file works.
