That's exactly the artifact I'd want to see for the product question — a real, tight, seven-step protocol written *for* an agent to read at session start. Good, now I have what I need for both reviews.

## Technical review

**Architecture, honestly assessed:** ~8,900 lines of Go, 31 non-test files, 53 CLI commands. The core spine — storage, verification, routing, orchestration — is genuinely well-engineered: additive-only SQLite migrations checked via `PRAGMA table_info` rather than blind `ALTER`s, a unique-index-as-arbiter for claim atomicity (proven correct by an 8-*process* race test, not just goroutines), a router kept as a pure function (no I/O, no model calls — that boundary is explicitly protected in `AGENTS.md` itself), and a trust boundary (`Local`) that's been attacked and fixed twice now (once for the check-then-insert race, once for the `put`-is-guilty-by-default fix) rather than just asserted once and left alone. This is the strongest part of the codebase by a wide margin, and it earned that strength the hard way — through review passes that found real bugs, not through getting it right the first time.

**Where the numbers tell a less flattering story:** 16 test files against 31 implementation files, and of the eight commands `CHARTER.md` itself flagged as "built fast" and risky (`fleet`, `sync`, `scorecard`, `timeline`, `skill pack/check`, `skill-sync`, `explain`, `reject`), only `capture` has a test file. That's not a small gap — it's the exact gap the project's own planning document identified and then didn't close, twice now (I flagged it last review, it's still true this review). The core thesis machinery is well-tested; the surface built during the fast experimentation phase (R10–R13) isn't, and that surface is now large enough to matter.

**Process observation, stated plainly because it's been a repeating pattern:** across this project's history, every "let's pause and consolidate" plan has been followed by more building instead. It's happened three times now. Twice it turned out fine because the thing that got built instead was good (the review pass, R12/R13). This time there's no such rescue — the untested surface is just untested. I'd treat "actually execute `CHARTER.md`'s P0 list" as the single highest-value next session, not because anything's on fire, but because the pattern of deferring it is now well-established enough to be a real risk in itself.

**On R12/R13 specifically, from a purely technical lens:** this is unusually good engineering discipline — a *pre-declared* falsifier, a controlled A/B with identical spec/DoD-gate/environment across arms, isolation bugs caught and the run voided/redone rather than the contaminated data being kept. That's the rigor of an actual experiment, not a demo. Most projects at this stage don't measure whether their own headline feature helps; this one did, published the result even though it was unflattering, and updated its guidance accordingly. That's rarer and more valuable than the fleet feature itself.

## Product review

**Would Claude Code CLI users like it?** I think yes, for a specific and fairly narrow slice of users — people already running multiple long-lived agent sessions against the same repo and getting bitten by exactly the failure modes WARD targets: an agent re-discovering the same gotcha every session, or confidently reporting something's done when it isn't. For that person, `AGENTS.md`'s seven-step protocol is a genuinely well-designed onboarding artifact — it's short, it's imperative, it tells the agent what *not* to do (don't hand-type `memory put`, don't retry past two escalations, don't bypass the trust boundary) as clearly as what to do. That's rarer than it sounds; most "agent memory" tooling I've seen is optimized for what a human reads, not what an agent should mechanically follow.

The honest limiting factor: most Claude Code users today are one person, one session, iterating quickly — closer to R12's "solo" arm, which *WARD's own data says wins* at that scale. That's not a knock on the tool, it's just an accurate read of who benefits: this is infrastructure for the coordination problem, and most sessions don't have a coordination problem yet. The people who'd genuinely want this are the ones running multiple parallel Claude Code sessions or a fleet-style setup already — a smaller but real audience, and one that's growing as agent-driven development scales up.

**Would Anthropic's models specifically like it, as an agent operating it?** I think there's something real here worth naming precisely: the trust-gated verify step is solving a problem models genuinely have — confidently treating stale context as current fact, exactly the "chef doesn't see the code" failure mode that kicked off this whole project. A protocol that mechanically forces "unverified context counts as a miss, not a fact" is compensating for a real, common failure mode in how models reason over retrieved context, not an imagined one. The two-escalation-then-stop-for-human rule is similarly well-matched to how models actually fail — not with an error, but with confident wrongness that compounds if left to retry indefinitely.

Where I'd be less confident: the seven-step protocol asks a lot of *procedural discipline* from a model — always check `ward brief` first, always route through the pool, never hand-type `memory put`, always `handoff` before ending. That's the same category of thing chef's original ceremony overhead was criticized for (qwen-auth's own feedback, all the way back at the start of this project) — except now it's aimed at compliance with WARD's protocol instead of chef's artifact lifecycle. A model under pressure, low on context, or just imperfectly instruction-following might skip step 4 (claim before touching shared state) exactly when it matters most, and nothing in the protocol *enforces* that a model actually read `AGENTS.md` before acting, the way the trust boundary is enforced in code. R12 is the sharpest evidence for this concern: even with the tool available, the model doing solo work often just didn't need it, and did fine without it. That's the right outcome, but it also means "will a model actually use this correctly and consistently" is still closer to a social/instruction-following bet than a technical guarantee — which is a fundamentally different kind of risk than the code-level guarantees this project has otherwise earned.
